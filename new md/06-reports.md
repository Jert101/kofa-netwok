# 06 — Reports

**Status:** Not started
**Roles:** secretary and admin (generate), super admin (approve or reject), admin (archive)
**Depends on:** 04, 05
**Size:** L
**Migration:** 028

## 1. Purpose

The monthly attendance report is the core deliverable. Keep the two-step generate-then-approve workflow and make it safer to use: preview before generating, reasons when rejecting, no report stuck in limbo, exports, and storage that scales.

## 2. Current behavior

(repo `README.md` §5.5–5.7)
- Eligibility: the last Sunday of the month from 20:00 church time, one report per month. Admin can bypass the schedule and backfill last month.
- The secretary picks sessions (columns) from a list of sessions with at least one record.
- The server builds the grid, renders a PDF (jsPDF), and saves the row with `pdf_storage_path` holding **base64 bytes** and `summary_json` v4.
- With a super admin PIN set, the report is `pending`, archiving is deferred, and the super admin is notified. Without one it is `approved` at once.
- Super admin views the PDF, then approves or rejects. Rejected reports unlock the month; regenerating deletes the rejected row.
- Admin can archive an approved month's data. Once a non-rejected report exists, the month's attendance is locked.

## 3. Problems found

| # | Problem |
|---|---|
| P1 | Rejection has no reason, so the secretary has to ask around. |
| P2 | The rejected report is deleted at regenerate. There is no history of what was rejected or why. |
| P3 | The secretary cannot see the grid before generating. Mistakes surface only after the super admin review. |
| P4 | Pending appeals are not flagged at generation. |
| P5 | A pending report can wait forever. Nobody is reminded. |
| P6 | PDFs are stored as base64 in the database. The README already notes the ceiling. |
| P7 | `summary_json` does not keep per-cell data, so nothing but the PDF can be rebuilt once data is archived. |
| P8 | No spreadsheet export. |
| P9 | The super admin has to open a PDF to see any numbers. |

### RPT-1 Reports hub

- **Status strip** driven by `can-generate`:
  - Ready to generate
  - Outside schedule — "Opens Sun 26 Oct, 8:00 PM"
  - Pending approval
  - Already exists
- **Past reports** table: month, status badge, generated by and when, reviewed by and when, review note, data archived. Actions: Download (approved only), Details, and the Archive switch (admin only).
- Non-approved rows show a status pill instead of a download button, as today.

### RPT-2 Generate wizard

A step dialog (full screen on phones), started from the status strip.

1. **Month.** Defaults to the current eligible month. Admin can pick the previous month or bypass the schedule.
2. **Sessions.** Checklist from `month-sessions`: date, Mass, attendance count. Select all and none. Low-turnout sessions are labelled "Low turnout" (below half of the month's median). At least one is required.
3. **Preview.** The real grid on screen: members down the side, sessions across, green served, red absent, dash not scheduled, remarks and totals. Scrolls inside its own container. Warnings above it:
   - "N appeals are still pending for this month."
   - "N active members have no attendance in the selected sessions."
4. **Confirm.** Summary of the choices. **Generate report** runs behind the blocking overlay. The server rebuilds the grid; the preview is never trusted.

The preview and the PDF use the same grid builder (`weekend-grid.ts`), so they cannot disagree.

### RPT-3 Reject with reason; keep history

- The super admin must give a reason: presets (Missing sessions, Wrong attendance, Other) and a note of at least 5 characters. Stored as `review_note`.
- The secretary sees the reason in the row and in the notification body.
- Rejected reports are **kept**. The unique month index becomes a partial index that applies only to non-rejected rows (`WHERE status <> 'rejected'`). The "delete the stale rejected row at regenerate" step is removed.
- History shows every attempt: generated, rejected with reason, regenerated, approved.
- The month unlock rule is unchanged: rejected rows do not lock or block.

### RPT-4 Super admin console

- `/super-admin`: cards for **Pending review** (count, oldest waiting) and recent decisions.
- `/super-admin/reports`: tabs Pending, Approved, Rejected. Each card: title, month, generated by, when, waiting time.
- **Review view** for a pending report:
  - On-screen summary: sessions included, attendance total, member count, members with zero attendance, and the grid (from the stored snapshot).
  - **View PDF** opens the stored file. Where inline PDF viewing is unreliable (iOS Safari), it opens in a new tab.
  - **Approve** (confirm) and **Reject** (reason dialog).
- Only `pending → approved|rejected` is allowed. Anything else returns 409.

### RPT-5 Pending reminders

- Daily cron. A pending report older than 48 hours sends a reminder notification to the super admin and admin. One reminder per day, at most three.
- Combined with AUTH-7, a pending report cannot be orphaned.

### RPT-6 Archive

- The Archive switch in past reports stays admin-only and idempotent.
- Turning it on asks for confirmation: "Move {Month} sessions and attendance to the archive and remove them from live tables? This cannot be undone."
- Shows "Archived on {date}" and counts (sessions, records). The legacy archive-at-generate toggle (default on, admin can disable) is kept for the no-super-admin path.
- Archived data continues to feed top servers, inactive members and member profiles.

### RPT-7 Exports

- **XLSX** and **CSV** of the grid for approved reports, same visibility as the PDF.
- Version 5 of `summary_json` stores the full grid so exports and the review view work after archiving:

```txt
summary_json v5 adds:
  grid: {
    columns: [ { date, massName, sessionId } ],
    rows:    [ { memberId, name, cells: ["S"|"A"|"-"], served, remarks } ]
  }
```

- Older v4 reports show the PDF only and a note that exports are unavailable for them.

### RPT-8 Storage

- New reports store the PDF in a private Supabase Storage bucket `reports`. `pdf_storage_path` holds the object path and a new column `pdf_storage_kind` says `inline` (old base64) or `object`.
- Download routes keep their role checks and stream the file from storage with the service role. No public URLs.
- Existing base64 rows keep working. A one-off script can move them later.

## 6. Data (migration 028)

```txt
reports
  + review_note text NULL
  + pdf_storage_kind text NOT NULL DEFAULT 'inline'     -- 'inline' | 'object'
  DROP UNIQUE(report_month)
  CREATE UNIQUE INDEX reports_month_active ON reports(report_month) WHERE status <> 'rejected'

Storage bucket: reports (private)
summary_json v5 (no DDL)
```

Any code that assumed one row per month must be found and updated (`can-generate`, list, lock check). Search for `report_month` before merging.

## 7. Business rules

- Window rule: last Sunday of the target month from 20:00 in church time, unless admin bypass. Extracted as a pure function `canGenerateMonthlyReport(now, month, tz, existing)`.
- One non-rejected report per month.
- Generation requires at least one selected session, and every selected id must belong to the month.
- With a super admin PIN: status `pending`, notification, archiving deferred. Without: status `approved`, archive per toggle.
- Approve and reject stamp `reviewed_by` and `reviewed_at`.
- Downloads and exports write `report_downloaded` audit rows.

## 8. Edge cases

- The last Sunday is the 31st. The window opens that evening; test it.
- Two people press Generate at once. The partial unique index rejects the second with 409.
- The super admin PIN is set after a report was created without approval. That report stays approved.
- A report is approved and archived, then a member is deactivated. The report is a snapshot and does not change.
- Preview and generate are minutes apart and attendance changed. The generated report reflects the data at generation time. The wizard says so.
- Storage upload fails. The report row is not created, and the user sees a retryable error.

## 9. Acceptance criteria

- [ ] The status strip shows the correct state and, when outside the window, the exact opening time in church time.
- [ ] The preview grid matches the generated PDF cell for cell.
- [ ] Pending appeals produce a warning in the wizard. Secretary cannot continue; admin can after confirming.
- [ ] Rejecting requires a reason. The secretary sees it in the row and in a notification.
- [ ] After a rejection, the old row remains in history and the month can be regenerated. No duplicate active report can exist.
- [ ] A report pending for more than 48 hours triggers a reminder to super admin and admin.
- [ ] The super admin can decide a report from the on-screen summary without opening the PDF.
- [ ] XLSX and CSV downloads match the grid, for v5 reports, and only for approved ones (admin and secretary).
- [ ] New PDFs are stored in Storage; old inline PDFs still download.
- [ ] Archiving is idempotent and asks for confirmation.
- [ ] Audit rows exist for the Reports actions in module 02.
